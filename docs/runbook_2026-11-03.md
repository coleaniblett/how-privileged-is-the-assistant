## Launch order

OLMo first (the reference family and the cheapest to debug), then Qwen, then Gemma 4 31B.

All three use the same pattern; `RUN=capstone` is the default and the outputs go to `results/capstone/<family>/`. Extra args
after the script name go to both `core.score` and `core.generate`; `SCORE_ARGS` goes to `core.score` only.

### 1. OLMo 3 7B (base, SFT, DPO, Instruct)

```bash
CLEAR_CACHE=1 FAMILY=olmo3-7b bash scripts/run_gpu.sh 2>&1 | tee logs/olmo3-7b.log     # mkdir -p logs first
```
- Disk: 4 checkpoints of about 15 GB; with `CLEAR_CACHE=1` each is removed after use, so the peak is one checkpoint plus the check's
  5 GB margin (none is cached now). `CLEAR_CACHE=auto` would keep them (they are under 20 GB).
- Time (estimate, not measured on OLMo): about 6-8 min scoring all 1190 texts x 3 slots in fp32 per checkpoint (Qwen3-8B, same size,
  took 24 s per 270 sequences, so about 5 min for 3570), about 5 min for 300 samples, plus download. About 1 to 1.5 hours in all.
- The role-swap and coin-toss extras are skipped when `FAMILY` is set (they are OLMo-only); to run them, use the legacy
  `bash scripts/run_gpu.sh` (writes `results/olmo3-7b/`).

### 2. Qwen3-8B (base, instruct)

```bash
FAMILY=qwen3-8b bash scripts/run_gpu.sh 2>&1 | tee logs/qwen3-8b.log
```
- Disk: base 16.4 GB to download (instruct is cached); both stay cached (under 20 GB). About 35 GB for the two.
- Time: scoring measured 24 s per 270 sequences (fp32, all on the GPU), so about 5.5 min per checkpoint for all texts; generation about

- **Decision first:** the assistant-slot rendering (think block) changes the assistant role-specific term and therefore the asymmetry; see

### 3. Gemma 4 31B (base, instruct) with CPU offload

Needs 67.5 GB free for the first checkpoint (62.5 GB of weights plus the margin) and about 95 GB of RAM (the fp32 weights are about 125 GB,
30 GiB of them on the GPU; the machine has 1.5 TB). Make room first, for example after the Qwen run:
```bash
uv run python -m core.hf_cache free Qwen/Qwen3-8B ; uv run python -m core.hf_cache free Qwen/Qwen3-8B-Base   # about 33 GB
df -h / | tail -1
CLEAR_CACHE=1 FAMILY=gemma4-31b SCORE_ARGS="--n-per-set 100" bash scripts/run_gpu.sh 2>&1 | tee logs/gemma4-31b.log
```
- Time (*measured* in the pilot): scoring 270 sequences takes 603-630 s with offload at batch size 4. With `--n-per-set 100` (4 sets x 100 texts x
  3 slots = 1200 sequences) that is about 45 min per checkpoint; all 1190 texts would be about 2.3 h per checkpoint. Generation in int8:
  573 s per 60 samples of 120 tokens, so 300 samples is about 48 min per checkpoint. Total about 3 h with `--n-per-set 100`, about 7.5 h
  without, plus two 62.5 GB downloads (not timed). Run it under `tmux`/`nohup`.
- Use the same N for the analysis: `--first 100` (below). The pilot used 30.

## Flags, judging, analysis

The run script already runs the flags (`measures.vestigial_regression.flags`) and the default analysis for each family. Judging is separate, because it needs the key:

```bash
# 0. what it will cost, calling nothing (prices are not built in: pass the current price list, $ per million tokens)
uv run python -m measures.vestigial_regression.judge run --dry-run --price-in X --price-out Y \
   --samples results/capstone/*/core/generations/*.jsonl --out /dev/null

# 1. validate the judge BEFORE using it on the runs: a teammate labels judge_validation/sheet.csv by hand (see below), then
uv run python -m measures.vestigial_regression.judge validate \
   --human measures/vestigial_regression/judge_validation/sheet.csv --out measures/vestigial_regression/judge_validation/agreement.md
#    default bar in the README: revise judge_prompt.md if raw agreement is below 80%; bump `prompt_version` when you do.

# 2. judge every checkpoint (cached by sample hash, so reruns are free)
for fam in olmo3-7b qwen3-8b gemma4-31b; do for f in results/capstone/$fam/core/generations/*.jsonl; do
  uv run python -m measures.vestigial_regression.judge run --samples $f \
     --out results/capstone/$fam/vestigial_regression/judge/$(basename $f)
done; done

# 3. the locked analysis (same texts for every family: --first N must match the scoring)
uv run python -m measures.vestigial_regression.analyze --locked --run capstone --first 100
#    -> results/capstone/vestigial_regression/locked/locked.md and locked.csv
```
- API cost: about 1,080 input tokens per request (measured on the validation sheet: 64,890 estimated input tokens for 60) and about 60 output tokens.
  The capstone has 8 checkpoints x 300 samples = 2,400 requests, so about 2.6 M input and 0.15 M output tokens (token counts are a
  characters/4 estimate; multiply by the current Claude Sonnet 5.5 prices). The validation sheet is about 65 k input tokens; the pilot-label
  comparison (`judge pilot`, 105 requests after de-duplication) about 114 k.
- The pilot-label comparison is provisional only (the labels were written by the agent that ran the pilot):
  `uv run python -m measures.vestigial_regression.judge pilot` once the key is set.

## Decisions for Cole

1. **Qwen3 assistant-slot rendering (think block). DECIDED 2026-11-02: ON is the primary (pre-declared), OFF the robustness check; the
   config default is now `True` and the overnight run scores both (`docs/decisions.md`).** Original text: `config.FAMILIES["qwen3-8b"]["assistant_think_block"]` was `False`, as in the pilot (the
   assistant slot is the header followed directly by the text). Setting it to `True` opens the slot with the empty `<think>\n\n</think>\n\n`
   that Qwen3's non-thinking generation prompt adds, the analogue of Gemma's thought channel (which made an earlier ~1 nat slot effect an
   artifact). It matters more than the pilot report said: it changes `asst@asst`, so the assistant role-specific term and **the asymmetry,
   the NLL arm's primary quantity**, not just a descriptive slot effect. It also affects logit distortion's `asst@asst`. Decide before the Qwen
   run; to compare, score the instruct model both ways with `--out` to different dirs (about 5 min each). I did not change the default.
2. **Minimum judge-arm rate difference** that counts. Open in the README. `analyze.py --locked` fires the judge arm when the
   non-user-voice rate change is positive with a CI excluding zero and reports the magnitude; it applies no minimum.
3. **How much of Gemma to score.** I recommend `--n-per-set 100` (about 3 h) over all texts (about 7.5 h); the pilot used 30. The analysis must
   use the same N for all families.
4. **Spearman across the arms** uses post-trained points only (base is zero by construction), one NLL asymmetry per point (bits per byte, mean of
   the two user sources) against the judge's non-user-voice rate change. With about 5 points it is descriptive.
5. **Handoff markers.** The brief named Gemma `<|channel>` and Qwen `<think>`; I added the closing tags (`<channel|>`, `</think>`) because in
   the exploration samples Qwen3-8B never writes `<think>` (0 of 205) but writes `</think>` without it in 66, and 4 Gemma samples have `<channel|>`
   alone. The extra markers flag a handoff without shortening the user portion.
6. **Output layout.** `--family` writes to `results/<run>/<family>/...` with run `capstone` by default (not the OLMo-only `results/<run>/` of AGENTS.md,
   which still applies when no `--family` is given). AGENTS.md's Outputs section was not changed; update it if you keep this layout.
7. **`token_loop` needs token ids.** `core.generate --save-ids` stores `continuation_ids` (off by default so core's output format is unchanged;
   `run_gpu.sh` passes it when `FAMILY` is set). Generation files without them are re-tokenized by the flags, which can merge a repeated character
   and miss a loop.
8. **Prefill set.** `data/prefill_100.jsonl` is the first 100 distinct first sentences of the held-out WildChat user turns already in `texts.jsonl` (same rule
   and order as the original 20), not a fresh draw; it inherits the Dolci filter through `texts.jsonl`.
9. **Cache clearing** never removes a checkpoint that was already cached when `run_gpu.sh` started (the exploration's rule); `CLEAR_CACHE=auto` clears
   only checkpoints of at least 20 GB, `1` clears every one it downloaded.
10. **Authorship sets.** UltraChat is `openbmb/UltraChat` (the version in the cache); the length filter drops 76% of its pairs, so the kept replies skew short
    (median 164 tokens). 62% of the oasst1 candidates were removed as present in Dolci. Scoring them is not part of the launch commands above; add
    `--dataset data/texts_authorship.jsonl --out results/capstone/<family>/core/scores_authorship` to `core.score` runs if Grace wants them.
11. **Judge details.** A reply that does not parse is asked for once more, then recorded as `invalid` (and counted in no category). The judge
    prompt wording (v1) is mine; the agreement check is what tells whether to revise it.

## Resilience: surviving a reset (added after the first overnight launch was lost with its session)

The first launch ran as a child of the agent session and died with it two minutes in (no output lost; the Gemma base download survived in the HF cache).
Use these instead of running the driver directly:

```bash
bash scripts/overnight_launch.sh          # starts (or confirms) the collection in a tmux session, 'overnight'; safe to run again
python3 scripts/overnight_status.py       # alive? current task, finished outputs, failures, disk (read-only, any session)
tmux attach -t overnight                  # watch it; detach with Ctrl-b d
uv run python scripts/overnight_report.py # (re)generate docs/overnight_2026-11-03.md from the run's records
```
- **tmux** is its own server process (parent PID 1), so a reset of the agent session, an SSH connection or a terminal does not touch it.
- **A supervisor restarts the driver** if it dies for any reason (crash, kill, the OOM killer), after 60 s, up to 8 times; the driver skips finished work.
- **Outputs are atomic:** a task writes into `.tmp_<task>/` and the files are moved into place only after a clean exit, so a kill never leaves a truncated
  `*.csv`, `*_tokens.parquet` or `*.jsonl`. An interrupted attempt's log is kept as `<task>.interrupted-<time>.log`.
- **Children die with the driver** (`setpriv --pdeathsig`) and any orphan is swept at start, so a restart cannot collide with a leftover process on the GPU.
- **One driver, one supervisor** (locks); `SIGHUP` is ignored; a heartbeat in `results/capstone/logs/status.json` shows liveness.
- Drilled live: `SIGKILL` of the driver mid-task: the scorer died within 3 s, the supervisor restarted the driver after 60 s, which removed the temp directory,
  kept both interrupted logs and restarted the task.
- **Not covered:** a restart of the container itself (tmux goes with it): run `bash scripts/overnight_launch.sh` again and it resumes. The agent's own
  monitoring (notifications) does not survive a reset either; use the status command.
